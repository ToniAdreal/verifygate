VerifyGate

AI proposes. Deterministic checks dispose. The evidence record proves it.

VerifyGate is a pre-delivery verification harness for coding agents. A coding agent (or a human) submits a code change plus a task spec; VerifyGate runs the spec's deterministic checks — unit tests, reproduction scripts, lint/type gates — in a sandboxed copy of the candidate, and only artifacts that pass receive a signed, replayable evidence record: a hash-chained JSON document capturing exactly what was checked, the commands run, their outputs, and the resulting PASS/FAIL.

The LLM (NVIDIA Nemotron via Nebius Token Factory) may propose patches and explain failures. It never decides PASS/FAIL. Verdicts come only from deterministic validators: exit codes and assertions. The model never grades its own homework.

Verify a record yourself — no re-run, no keys

A record's point is that a third party can check it without trusting the producer. The standalone verifygate verify command recomputes the hash chain and signature of a record (or of every attempt in a repair report) and can bind it to the spec file and candidate directory on disk:

python3 -m verifygate verify --record samples/evidence_real_repair.json \
    --spec samples/spec.json --candidate samples/failing
# -> RECORD INTACT: 2 record(s) verified

Tampering with a verdict, a check result, a diagnosis, or a sealed token-usage figure fails verification. No checks are re-run and no network is needed.

Replay a record yourself — re-run and compare

verify proves a record is intact; verifygate replay proves it is reproducible. Replay re-runs the checks and compares the verdict and every per-check result against the sealed record. For a repair report, each patched attempt is reconstructed from the original candidate plus the patch recorded in the report — the ephemeral temp copies the loop once pointed at are never needed:

python3 -m verifygate replay --record samples/evidence_real_repair.json \
    --spec samples/spec.json --candidate samples/failing --mode judge
# -> REPLAY MATCHED: 2 record(s) reproduced

Verdicts come from the deterministic checks, which are mode-independent, so even a real-mode record replays in Judge Mode with zero keys and zero model calls. A candidate edited after the fact, or a tampered record, does not reproduce.

Run it yourself (Judge Mode — zero keys, zero network)

Judge Mode swaps the LLM for a deterministic mock adapter: every validator still runs for real — only the words (patch proposals, explanations) are template-rendered. From a clone of the repository:

python3 -m pytest -q

# Passing candidate
python3 -m verifygate run --spec samples/spec.json \
    --candidate samples/passing --mode judge
# -> VERDICT: PASS

# Failing candidate, then the repair loop
python3 -m verifygate run --spec samples/spec.json \
    --candidate samples/failing --mode judge
# -> VERDICT: FAIL, with a diagnosis in the evidence record

python3 -m verifygate repair --spec samples/spec.json \
    --candidate samples/failing --mode judge --max-rounds 3
# -> attempt 0: FAIL, attempt 1: PASS

A scripted end-to-end rehearsal from a pristine copy of the tracked tree ships in the repository as scripts/rehearse.sh.

Real mode

With a Nebius Token Factory credential configured, --mode real drives NVIDIA Nemotron for patch generation and failure explanation through the exact same loop. Every real model call (model, purpose, token usage) is sealed into the evidence record's hash chain, so the token bill is as tamper-evident as the verdict. This hosted page is static and runs Judge Mode material only; no candidate code is executed here.
